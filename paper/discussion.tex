\section{Discussion}\label{sec:discussion}

The book is not closed on the design of straight-line asynchrony. Communities are actively working on the usability and the safety of asynchronous systems. For usability many are concerned about the function coloring problem first introduced by \citet{nystrom_what_2015}, and others are designing increasingly sophisticated type systems to statically check the safety of asynchronous program.

\paragraph{Function coloring} A common complaint raised online about async/await is its virality in the codebase; once one async function is called, seemingly the entire codebase must use async/await syntax. Async/await is infectious because of the function coloring problem: An async function may be called only from another async function. Libraries are published as either sync or async and clients who use async libraries must write async applications.

Asynchrony is infectious for good reason. An async function does not execute the same way a synchronous one does, the asynchrony inverts the flow of control. Although the async/await syntactic abstraction reinverts the written code, the execution is fundamentally inverted. Despite the mismatch in execution semantics between sync and async code, several communities are trying to solve, or mitigate, the function coloring problem. Here we will highlight one particularly interesting attempt by the Zig community and show that it merely \emph{shifts} the coloring elsewhere.

\begin{wrapfigure}{r}{0.4\textwidth}
\begin{lstlisting}[language=Pseudo,numbers=none]
fn producer(io, q):
  q.put(io, "hello")

fn consumer(io, q):
  return q.get(io)

fn run(io):
  q = io.UnbufferedQueue()
  a = io.concurrent(producer(io, q))
  b = io.concurrent(consumer(io, q))
  print(await b)
\end{lstlisting}
  \label{fig:zig}
\end{wrapfigure}

Zig is a new general-purpose programming language designed for maintaining robust, optimal, and reusable software. We do not include the semantics of Zig async/await in the main text because the implementation is still unfinished, with the current design expected to land in late 2026. One key feature of Zig is that there are no hidden allocations and the language does not provide a default allocator. Programs that allocate memory are parametric over an allocator, which means that clients of libraries can dictate how allocations occur.

To introduce asynchronous execution the Zig developers created an \code{Io} interface that will additionally need to parameterize functions that wish to perform \abbr{io}. Library clients can then pass a synchronous, green-threaded, or coroutine-based\footnote{The design of Zig's stackless coroutines is still being designed and will not stabalize with the other implementations.} implementation of the \abbr{io} interface to libraries depending on their needs. Library code must still be written in an asynchronous style if developers wish to take advantage of asynchrony.

We argue that Zig functions remain colored, however, they are colored in \emph{semantics} and correct usage is not checked by the compiler. \Cref{fig:zig} provides a pseudocode representation of a Zig function written to take advantage of concurrency.\footnote{The full Zig code is available in \Cref{appx:zig}.} As written, the code is only valid with a threaded \abbr{io} implementation --- more than one thread must be available --- or the stackless-coroutine implementation that will not be available for some time.

\paragraph{Where do we go from here?}

We set out to examine the space of straight-line asynchrony, confused by some statements we read in individual language descriptions. In particular, as we note in \cref{s:sync-quotes-from-langs}, these languages motivate async from a perspective of similarity to synchrony, which we found difficult to reconcile. Our design space exploration demonstrates the numerous ways in which this analogy fails.

One main use for our exploration is to educate developers. Developers transitioning from one language to another carry their prior knowledge --- whether explicitly or tacitly --- to make sense of the new in terms of the old. It is then especially confusing when the new language has the same keywords and similar description as the old one, but with a different semantics (especially when the semantics are subtly different). We believe the kind of description we have provided --- especially \cref{tab:dims-overview} --- can be very helpful to a developer making this transition. Conceivably, one could even build tutoring systems around this table and around the semantics in \cref{sec:semantics} to help developers actively build new mental models.

We also believe our exploration will inform designers of languages adding or modifying async features. For one thing, our taxonomy may help designers realize how many dimensions there even \emph{are}, so that they can make deliberate decisions (using the trade-offs we describe) rather than ending up with semantics that are an accidental consequence of implementation choices. For another, once they have chosen a point in the space, they may find other languages already in that space with which they can experiment to ensure they want the same consequences. They may even be driven to some choices simply because they are trying to attract developers currently using one of the other languages. Finally, they can document their language to higlight where their language sits in this space, and how it differs from other languages with similar-sounding features, to help developers both understand their motivations and become able to use the language effectively without too much trial-and-error.
