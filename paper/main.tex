\section{Introduction}

Contemporary programming languages make efficient use of hardware resources. Multithreading with coarse-grained parallel computations has long been the de-facto standard to take advantage of hardware resources. However, the landscape of modern languages have adopted flavors of \textit{asynchronous programming,} which is based on fine-grained suspendable computations. 

Unlike parallel programming with multiple threads, concurrent programming interleaves computations for better concurrency to suit the needs of modern programs that wait for user inputs, system IO, etc. The promise of ``async/await'' systems is that concurrent code looks like synchronous code and that developers can use familiar reasoning facilities to understand their code's execution.

The design of ``async/await'' systems has organically grown out of the desire for async programs to syntactically resemble synchronous programs and the design constraints of retro-fitting a concurrent system atop a synchronous base. Async systems hide complex control flow and a myriad of design decisions, which impact the developer, behind the facade of familiar syntax. Our goal is to shed light on the design decisions of contemporary async systems, the impact these decisions have on developers, and the semantics of popular systems in use today. We describe the landscape of asynchronous systems in four parts: 

\begin{enumerate}
  \item \textbf{We motivate the work with case studies about the pitfalls of async/await systems.} We show that developers struggle to understand the behavior of async programs due to inconsistent terminology, mismatched guarantees, and divergent semantics between languages.

  \item \textbf{We outline the design dimensions of an asynchronous system.} Adding asynchronous programming to a language natively requires great engineering effort. The language gains new syntactic constructs, compiler transformations, and a runtime system that all work together to provide the desired look and behavior. We find that many of these systems share a common set of architectural components, but differ in how these components are assembled. We outline these decisions and clarify mixed terminology that exists in the wild.

  \item \textbf{We provide operational semantics for several contemporary programming languages' asynchronous systems.} We grow the operational semantics from the $\lambda$-calculus into the complex systems that exist in the wild. We show how the design decisions affect the operational behavior of each language compared to the others.
    
  \item \textbf{We provide a mapping of design decisions to properties of programs in the resulting language.} Language designers make trade-offs when designing their async systems. We highlight how these trade-offs impact the resulting programs developers write. This information can help developers understand the behavior of their programs, and inform language designers of the downstream impact of their design decisions. We encourage designers going forward to consider the properties they wish to provide to developers and design their systems accordingly.
\end{enumerate}

\section{Motivation}

The design of async/await systems has organically grown out of the desire for async programs to syntactically resemble synchronous programs. Before async/await existed, langauges relied on callbacks, and complicated user-defined objects to model concurrent, even-driven computations. However, all of these approachers were verbose and unsatisfying. \Cref{fig:motivation:evolution} shows the evoluation of a piece of code from synchronous, callback-based, promise-based, and finally with async/await.

\end{displayquote}

\begin{displayquote}%swift

This gets particularly problematic when many asynchronous operations are used, error handling is required, or control flow between asynchronous calls gets complicated. \textit{This proposal describes a language extension to make this a lot more natural and less error prone.}~\cite{noauthor_swift-evolutionproposals0296-async-awaitmd_nodate}
\end{displayquote}

\end{displayquote}

\begin{displayquote}%c#
  \textbf{(\CSharp{})} \textit{Notice first how similar it is to the synchronous code.} \ldots The control flow is completely unaltered, and there are no callbacks in sight. The shocking reality is that the async/await example provided in \Cref{fig:motivation:evolution} is synchronous, the downloaded \abbr{uri}'s are sequentalized by the await in the loop body. For each cited language feature proposal, the proposers show examples of \textit{synchronous code} with async/await keywords sprinkled throughout, the reality is that the code is also altered when concurrency is desired.

In this section we expose the faulty logic that async/await is less complicated because it looks like synchronous code. Time is a dependency that cannot be fully abstracted, by hiding it behind keywords, developers require deeper knowledge of the system implementation than ever before.

\Cref{fig:wat:rust-drop} shows two possible versions of the forward function. In the first version (left), after profiling, you observe that the sending channel is empty for long periods of time and you'd like to log when it's empty for longer than five seconds. To do this, you would wrap the \code{recv} operation with a timeout, if the result is an error, the timeout occurred before the read happened. In this case you can log this gap in data and continue. In the second version (right), after profiling, you observe that the receiving channel is full for long periods of time and you'd like to log when it's full for longer than five seconds. The operation is the same as before, you wrap the \code{send} operation in a timeout and check the result.

Although these two scenarios sound harmless, if you choose the second version --- logging timeouts of the \code{send} operation --- you've introduced a bug in your code. The forward operation no longer forwards all packets, instead, it forwards only the packets that don't timeout. The expression \code{tx.send(msg)} consumes \textit{ownership} of the message in the buffer. If the timeout finishes first, it will free the memory associated with the concurrent send operation, which includes the message that was read. The accidental memory free comes from the \code{select!} statement that races the two computations against each other, freeing the ``loser.''

\subsection{Swift and the Overdrawn Bank Account}

Swifts actors are conceptually very similar to classes but advertised as safe to use in concurrent environments. Unlike classes, actors allow only one task to access their mutable state at a time, which makes it safe for code in multiple tasks to interact with the same instance of an actor. Following this definition, and dreaming of data-race-free code, you rewrite your banking application in Swift.

\begin{wrapfigure}{l}{0.49\textwidth}
  \begin{lstlisting}[language=Swift]
struct TransactionData { 
  amount : Double,
  /* rest elided */
}

actor BankAccount {
  var balance: Double = 100.0

  func withdraw(
    trans: TransactionData
  ) async throws {
    assert(0.0 <= balance, 
      "account balance negative")

    guard balance >= amount else {
        throw BankError.insufficientFunds
    }

    await verifyTransaction(trans)
    balance -= trans.amount
  }
}
  \end{lstlisting}
  \cprotect\caption{Swift actors conform to the \code{Sendable} protocol, meaning it is a ``thread-safe type whose values can be shared across arbitrary concurrent contexts.'' Although a value of \code{BankAccount} is thread safe, as written, a user can \textit{overdraw} from their account breaking the invariant that the balance is non-negative.}
  \label{fig:wat:swift-reentry}
\end{wrapfigure}

\Cref{fig:wat:swift-reentry} defines an actor \code{BankAccount} that manages the balance of a single clients account. The actor has two methods, \code{withdraw} and \code{deposit}. The main invariant that this actor must provide is that the \textit{balance is always non-negative.} When a withdraw transaction is started the code first checks that there's enough balance, verifies the transaction, and then modifies the account balance.

If you push this code in to production you'd likely wake up the morning after to find your bank in incredible debt as users overdraw copious amounts of money from their accounts. The issue is that when an actor method calls \code{await}, it suspends. While suspended, the actor is \textit{unlocked.} This means that a user could initiate a withdrawal, and while the first withdrawal is verifying the transaction, they could initiate a second withdrawal that would take the account balance below zero. Invariants checked before an await point may not hold after the await point, and so, the bank account is overdrawn.

If the \code{withdraw} method were instead synchronous the issue described above would not occur. Execution would enter the function, locking the actor, and the actor would not unlock until execution returned from the function. The actor remains locked in all callees because of the strict nesting behavior of stack frames. Asynchronous function calls break the strict nesting of stack frames, making it possible to exit the actor (via a suspend), only to reenter the actor within the same logical computation.

\subsection{\CSharp{} and the ``Exceptional'' Text Editor}

Windows Forms applications are popular motivation for concurrency. The application needs to run many computations and perform background tasks all while the main \abbr{gui} remains unblocked. Common advice is that all computation that is not rendering should be done outside of the \abbr{gui} thread. Swift even enforces this in the type system by placing all SwiftUI components to render within the \textit{main actor,} and all computations are \textit{escapable,} meaning they can be run on a different actor.

In the main application there is an open document and the \code{AutoSaveController} manages a background worker to periodically save the contents of the current document. Developers must consider exceptions from other threads, exceptions from called code, and even exceptions injected from the runtime.

\section{Design Dimensions} \label{sec:designdims}

The design of async/await systems rely on several key components. These range from language features that provide extra control-flow constructs to the langauge, to user-space objects that coordinate the runtime of the asynchronous code. In this section we will list what each of these constructs and objects are and their role in the larger asynchronous system. We will highlight the design decisions on how to assemble the pieces together and in \Cref{sec:semantics} we provide the operational behahvior of several contemporary programming languages, which assemble th pieces differently.

\subsection{Language Features}

To simply \textit{support} concurrent execution, programming languages need to provide advanced control flow that enables functions to suspend themselves for later resumption. The expressive power of a \textit{one-shot delimited continuation} is necessary, however, language designers may choose to not expose this functionality to users by containing this expressivity within compiler transformations. As we will discuss in \Cref{sec:semantics}, several languages need finer-grained control over memory allocation than \code{call/1cc} would provide, and indeed, most do not have direct support for capturing any variant of continuation. Therefore the language feature we present as a building block for concurrency is \textit{the coroutine.}

\subsubsection{Coroutines} As a generalization of the function, the concept of a coroutine has existed since the early 1960's~\cite{conway_design_1963}. Many researchers explored their use as a general control mechanism~\cite{knuth_art_1997,marlin_coroutines_1980,pauli_coroutine_1980,moody_coroutine_1980,wirth_programming_1985,griswold_icon_1983}, but it wasn't until 2009, when~\cite{moura_revisiting_2009} classified coroutine mechanisms and demonstrated their equivalence to one-shot delimited continuations. The design dimensions provided are: asymmetric vs.\ symmetric (e.g., the semantics of \code{yield}), stackful vs.\ stackless (e.g., where a \code{yield} can occur), and first-class vs.\ limited-use coroutines (e.g., are coroutines first class values).

In this section we will use the word coroutine to mean any implementation of coroutines along the three design dimensions. For most programming languages, functions support two operations: \ctrlop{call} and \ctrlop{return} --- here we consider throwing an exception as a \ctrlop{return} operation. A \textit{coroutine} supports three additional operations: \ctrlop{suspend}, \ctrlop{resume}, and \ctrlop{destroy}.

Coroutines contain data that must be preserved across suspension points and they contain data that only needs to be kept while the coroutine is executing. Data that must persist across suspension points is stored on the \textit{coroutine frame} and data that does not can go on the executing \textit{stack frame}. We will refer to the coroutine frame as The \Coro, an object that holds the state necessary to suspend and resume execution of the coroutine body.

The \ctrlop{suspend} operation allows a coroutine to suspend execution in the middle of the function and transfer execution elsewhere. Suspension points within a coroutine are typically identified by usages of a keyword, such as \code{await} or \code{yield}. When a coroutine hits a suspension point it first prepares itself for resumption by (1) ensuring necessary values are written to the coroutine frame, and (2) writing a value to the coroutine frame that indicates where the coroutine is being suspended at.

The \ctrlop{resume} operation can be performed on a suspended coroutine. Resumption will allocate a new stack frame, restoring the necessary state from the previous suspension, and execution will transfer to the point after suspension.

The \ctrlop{destroy} operation can be performed on a suspended coroutine and destroys the coroutine frame without resuming execution of the coroutine.

The \ctrlop{call} operation of a coroutine is similar to that of a function.\footnote{In fact, from the caller's perspective the two are equivalent.} However, instead of beginning execution of the coroutine body, the coroutine will first allocate a coroutine frame, write necessary data to the frame, and then possibly suspend to the caller. We say `possibly suspend` because a language may choose to continue coroutine executino until the first suspension point, or unconditionally suspend after creating the coroutine frame.

The \ctrlop{return} operation is highly dependent on the semantics of the language. When a coroutine returns the language may choose to suspend the coroutine, thus keeping The Coroutine alive, or it may destroy The Coroutine and return to the caller like a normal function. Execution is then returned to the caller/resumer.

\subsection{Library Components}

Asynchronous programs require a runtime to manage and schedule the execution of concurrent code. A runtime may be multithreaded, or single threaded, it may be provided by the language and its runtime, or as a third-party library. The runtime design is informed by the language feature exposed to suspend and resume execution of coroutines.

\subsubsection{Runtime Object} The runtime object, moving forward referred to as The \Task, wraps a \Coro{} into an object that can be passed around by the runtime system. Semantically, a \Task{} is simply a pointer to the underlying \Coro{} that represents the computation.

An important property of a \Task{} is that it's registered in the runtime system and is scheduled to execute in the near future. Unlike a \Coro, which will not execute unless explicitly resumed, a \Task{} is being watched and its execution \textit{scheduled} by the runtime.

\subsubsection{Scheduler} The scheduler is responsible for scheduling concurrent code to execute. Execution may take place on a single thread, green threads, or multiple OS-threads. For this work, we consider the implementation of the scheduler as a performance concern and not part of the operational behavior of asynchronous programs. The scheduler may have implications on fairness and termination, which we discuss in \Cref{sec:discussion}.

\subsection{Design dimensions}

A concurrent system requires the power of \Coro{}s, \Task{}s, and a Scheduler to push everything along. However, these pieces don't always fit nicely together and some careful assembly is required. For example, a designer may choose a different coroutine design based on the previous design of the language, which in turn introduces a constraint on all downstream decisions. In this section we provide five async/await design axes that pertain to the design and assembly of the core language and runtime building blocks discussed above.

Given the core set of architectural components outlined above, we highlight how a langauge's assembly of these components influences its operational behavior. In particular, for each language we provide an answer to the following questions:

\subsubsection{Eagerness} The Eagerness axis defines the eagerness of an async function application, the possible values are: \textit{lazy, semi-lazy, semi-eager,} and \textit{eager.} An eager application is where the current thread transfers execution to the body of the async function, until a suspend operation is called, at which point the application evalutes to a \Task{} value. A \textit{semi-}eager application evaluates immediately to a \Task{} value, but it is only scheduled for execution, the currently executing thread does not begin execution of the function body. A \textit{semi-}lazy application is where the current thread transfers execution to the body of the async function, until a suspend operation is called, at which point the application evalutes to a \Coro{} value. A lazy application evaluates immediately to a \Coro{} value, no code in the function body is executed.

\begin{wrapfigure}{r}{0.33\textwidth}
  \raggedright
\begin{lstlisting}[language=Rust,numbers=none]
async fn work(msg: &str) {
  print!("{msg}");
  tokio::task::yield_now()
    .await
}

#[tokio::main]
async fn main() {
  let c1 = work("A");
  let c2 = work("B");
  print!("C");
  c1.await; c2.await;
} // => CAB
\end{lstlisting}
  \caption{An example of a \textit{lazy} async function application. The above program always results in the print order ``CAB''.}
  \label{fig:designdims:eagerness-lazy}
\end{wrapfigure}

\subsubsection{Cancellation} The Cancellation axis defines the cancellation strategy of the system, the possible values are: \textit{none, polite, aggressive,} and \textit{unavoidable.} We say that a system provides no cancellation (none) if the developer must explicitly pass cancellation tokens to child \Task{}s, that is, the runtime system has no built-in mechanism for cancellation other than functions returning as normal. A \textit{polite} cancellation strategy allows callers to mark a cancellation flag in the \Coro{}, however, async computations must explicitly check this flag. Developers may choose to, or forget to, check the flag, and cancellation is not enforced. An \textit{aggressive} policy is one where any \code{await} expression may raise a \textit{cancellation exception.} We qualify this as a cancellation exception, because await points can raise exceptions if the awaited \Task{} raised an uncaught exception. Cancellation exceptions come from the runtime, not callees. A system provides \textit{unavoidable} cancellation if the cancelled \Task{} can not observe its own cancellation; unavoidable cancellation does not allow for \Task{}s to execute clean-up code.

\subsubsection{Suspension} The Suspension axis defines how the set of \textit{await} points relates to the set of \textit{suspension} points, the possible values are: \textit{static,} and \textit{dynamic.} A system has \textit{static} suspension points if the language guarantees that every await point suspends the current computation. A system has \textit{dynamic} suspension points if the set of await points is a superset of the set of suspension points. Asynchronous computations may complete synchronously, in fact, a large number do, and the runtime can decide dynamically whether to actually suspend the calling \Task{} or continue with the awaited value.

\subsubsection{Task Scope} The Task Scope axis defines how the execution of a \Task{} is scoped, the possible values are: region scoped, program scoped, and unscoped. A system enforces \textit{region scoping} if the lifetime of a \Task{} cannot extend past the lifetime of the \Task{} it was spawned from. Our definition of region scoping is similar to what others call \textit{structured concurrency}~\cite{}. A system enforces \textit{program scoping} if the lifetime of a \Task{} cannot outlive the program. \Task{}s are \textit{unscoped} if the program can terminate before running \Task{}s have terminated.

\subsubsection{Exception} The Exception axis defines how exceptions interact with \Task{}s, the possible values are: awaited, and reraised. A system has \textit{awaited} exceptions if trapped exceptions propagate out of \Task{}s at await points. A system has \textit{reraise} exceptions if an uncaught exception can terminate the program without awaiting on a faulted \Task.

\section{Semantics}\label{sec:semantics}

The key contribution of this paper is a precise description of the operational behavior of several contemporary asynchronous systems. To reduce the cosmetic noise we provide the operational semantics as extensions to a simple base language. By providing the semantics in layers we highlight the control features necessary for a given language's implementation and can more easily compare the operational behavior between two languages.

We now describe the configuration of the shared asynchronous grammar. \Cref{fig:lang:platform} defines the shared grammar constructs that encode the async runtime building blocks discussed in \Cref{sec:designdims}. We will refer to this shared grammar extension as the \textit{async platform.}

A \textit{frame}, $F$, is written $\langle e,\,l\rangle$ and consists of an expression $e$, along with a frame label, $l$. A \textit{frame label}, $l$, is either the name of the \Task{} this frame corresponds to, or \textit{sync} to denote a synchronous frame. A \textit{frame stack}, $FS$, is a list of frames --- essentially a thread. A \textit{process}, $P$, is a collection of frame stacks. A \textit{task queue}, $Q$, stores the asynchronous frames waiting to be run. The async platform provides a few additional expressions that we will describe here.

The $block\,e_{async}$ expression provides the barrier between synchronous code and asynchronous code. Languages may use a block expression to block a synchronous frame until the asynchronous expression has completed running. For most languages the block expression marks the \textit{runtime entry,} and when it returns, the \textit{runtime exit.}

The form \code{os/io} is the \textsc{OmniScient IO} operation provided by the runtime system. It models real-world \textsc{io} operations that would take some non-deterministic amount of time to resolve, like receiving packets from the network or querying a database. The form is ``omniscient'' because the resulting expression is provided to the form, e.g., \code{(os/io 5 "hello")}, which means the \Task{} will resolve to the value \code{"hello"} after \textit{at least} five time steps. Thus the form is deterministic in its evaluation \textit{value}, but not in its evaluation \textit{time.}

Each asynchronous language is automatically defined with the platform expressions and additional non-terminals. These represent the common operations and a base-set of interactions each asynchronous language will have with its underlying system. The \CSharp{} language and relation extension is provided in \Cref{fig:lang:cs}.

Rule \semrule{Async-App} applies an asynchronous function, placing the function body in a new frame at the head of the executing frame stack. This is a \textit{hot application}, because the function body is immediately running in the executing thread. This frame will continue to run until a suspension point is reached.

Rules \semrule{Await-Suspend}, \semrule{Await-Continue}, and \semrule{Await-Failed} demonstrate how await points are handled. Suspension points in \CSharp{} are a \textit{subset} of all await points. That is, the rules \semrule{Await-Continue} and \semrule{Await-Failed} show that if the awaited object is complete --- with a value or an exception --- the current thread will continue executing. There is no guarantee that an await point will ever suspend the current computation, therefore, await points are unreliable.


The grammar presented in \Cref{fig:lang:cs} does not include a $cancel$ expression. Therefore, we say that \CSharp{} has \textit{no cancellation policy}. If a computation is to be cancellable, the developer must encode this behavior themselves via standard communication mechanisms (e.g., channels, events).


When a \Task{} is created, via \semrule{Async-App} or \semrule{Task-Run}, it has no relation to its context. Furthermore, when a task is resolved, \semrule{Task-Return}, there is no check for the status of child \Task{}s spawned during its execution. \Task{} objects freely live as any other object in \CSharp, no rule states that a \Task{} must be awaited, or even that a \Task{} must finish executing. The rule \semrule{Unblock} does not check the queue or status of executing threads for unfinished computations. Therefore, we say that both tasks and exceptions are ignorable.

The operational semantics for \Swift{} are provided in \Cref{fig:lang:swift}. Rule \semrule{Async-App} creates a new frame with the function body and places this frame in the queue to be run soon. The application result is a \Task{} object. Therefore \Swift{} employes \textit{warm} applications, because the frame is enqueued to be run, but was not immediately run by the executing thread. 

The \Swift{} grammar includes a new \code{(cancelled?)} expression, which returns whether the executing \Task{} has been cancelled. Common programming practice for a computation is to check this function at appropriate times, and perform clean-up and raise a \code{CancellationError} when the return is true. A \Task{} requests cancellation by passing the \Task{} handle to the \code{(cancel e)} expression. We call this a \textit{polite} cancellation strategy, because \Task{} cancellation cannot be enforced. Cancellation is requested, but requires cooperation from the requested \Task.

The rules \semrule{Await-Continue}, \semrule{Await-Failed}, and \semrule{Await-Suspend} do not provide any guarantee on suspension. There fore await points in \Swift{} are not stable and only represent possible suspension points.

The result of an async application is a new \Task{} object, which is associated with the label $l$ of the calling frame. In other words, \Swift{} establishes a \textit{parent-child relationship} between a calling \Task{} and a spawned \Task. Rule \semrule{Task-Return} relies on this relationship to resolve a \Task{} only when all child \Task{}s have resolved. The parent-child relationship of \Task{}s creates a \textit{task tree,} where a \Task{} can only return once every node in its subtree has resolved. Therefore, no \Task{} can be forgotten.

Rule \semrule{await-Failed} shows that the exception from a failed \Task{} only gets reraised at an await point. The rule \semrule{Block} does not reraise any unawaited exceptions at runtime exit, therefore, even though a \Task{} cannot be forgotten, an exception can be ignored if a \Task{} is nevery awaited.

The operational semantics for \Python{} are provided in \Cref{fig:lang:python}. The language \Python{}, by itself, does not provide a runtime. This fact is reflected in the extended grammar, which provides the expressions \code{async/lambda} and \code{await}, but the language is not defined on top of our asynchronous platform. Therefore, it does not have frames, frame stacks, processes, etc.

The rule \semrule{Async-App} demonstrates that applying an asynchronous function results in a \Coro{} object. The function body is neither evaluated nor scheduled to run anywhere. Therefore, \Python{} employs \textit{cold applications.}

In the base language, a \Coro{} object can be either polled manually, via the \code{resume!} expression, or it can be \textit{awaited.} The rule \semrule{Await-Coro} shows that awaiting a \Coro{} is not syntactic sugar for polling the object, but instead it reduces to running the \Coro{} body. This has the effect of \textit{fusing} the \Coro{} stacks together, so a suspension point yields control to the caller of the outer \Coro.

The rule \semrule{Throw-In!} provides additional flexibility to $\lambda_{coro}$ language, specifically, the ability to raise an exception at the suspension point. The gained flexibility is not obvious in the core \Python{} language, but runtime extensions, such as \AsyncIO{}, will use this feature for cancellation.

The remainder of the system properties are not applicable to \Python{} without a runtime implementation. So we leave those unanswered in this section.

The de-facto runtime implementation in \Python{} is \AsyncIO{}. The operational semantics for \AsyncIO{} are provided in \Cref{fig:lang:asyncio}.

The rule \semrule{Task-Spawn} takes a \Coro{} object and turns it into a \Task{} registered with the runtime. This means that raw async function applications are still \textit{cold,} and must be explicitly registered with the runtime to be scheduled. The scheduling is \textit{warm,} because the spawned \Task{} will run soon, but not immediately.

The rule \semrule{Cancel} shows the use of the \code{cancel} expression. This expression takes a \Task{} object and marks it as cancelled. The next time the \Task{} is resumed, via the rule \semrule{Dequeue-Cancelled}, the runtime will not resume the underlying \Coro{} object, but use the \code{throw-in!} expression to raise a \code{CancelledError} at the suspension point. We call this cancellation policy \textit{aggressive} because an exception may be raised at any suspension point. Cancellation exceptions may be caught and ignored by the running computation, which is why the policy is not \textit{unavoidable.}

The rule \semrule{Task-Return} does not check for any child \Task{}s spawned during executions. However, the rule \semrule{Block-Exit} requires that all \Task{}s have resolved before the runtime exits. Therefore we say that \Task{}s are \textit{program scoped,} but not \textit{region scoped.}

The rule \semrule{Block-Exit} inspects the store $\sigma$ for any unawaited \Task{}s that have a trapped exception. If any such \Task{}s exist, the runtime will reraise the first exception it finds. Therefore, we say that exceptions are not ignorable.

\section{Properties ``The Table''}

Many programming languages share a semantic core that helps developers transfer from one language to another. Mutable variables, lexical scope, and eager evaluation, are examples of commonalities shared by a large number of modern languages. Developers rely on these commonalities and form a mental model of program execution to understand their program's behavior.

In the asynchronous world when a developer moves from language $A$ to language $B$ there are several pitfalls she may fall into. The first arises from \textit{inconsistent terminology.} Although contemporary async systems share a similar vocabulary, the semantic definition of a term may change between languages $A$ and $B$. Inconsistency amongst languages may introduce misconceptions in the developer's mental model of how an async system works that can lead to incorrect programs. 

The second pitfall is a mismatch in \textit{system guarantees.} The properties that async systems guarantee, or fail to guarantee, may lead to additional misconceptions when translating between languages. A mismatch in program guarantees may lead to an incorrect program execution profile or incorrect program behavior. We call these \textit{concurrency errors} and \textit{semantic errors} respectively. A concurrency error is when a program $P$ written in language $A$, $P_A$ can interleave computations $c_1, \ldots, c_n$ with interleaving $I$, such that that same program written in language $B$, $P_B$ cannot exhibit he same interleaving. A semantic error is when program $P$, written in languages $A$ and $B$ do not produce equivalent output for the same input $x$, that is $P_A(x) \not\equiv P_B(x)$.

In this section we will describe four system properties that lead to concurrency and semantic errors. These properties are:
\begin{enumerate}
    \item (\EEXN) A program with an unhandled exception terminates unsuccessfully
    \item (\ERUN) A computation eventually runs
    \item (\ETERM) A canceled computation eventually terminates
    \item (\APARENT) A computation is never left orphaned
    \item (\MPAR) A computation that could run on a different thread may
\end{enumerate}
