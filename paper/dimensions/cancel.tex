
% The Cancellation axis defines how a running task is cancelled, including how cancellation is signaled, if at all, and how a cancellation signal propagates through \task dependencies. A clear cancellation mechanism is an important feauture of the asynchronous programming paradigm. Cancellation is a sufficiently complex mechanism that it itself contains two design dimensions: \textit{cooperation,} and \textit{direction.}

% When a cancelled \coro or \task depends on another (\coro or \task) all dependencies are also cancelled. In this paper, we define a dependency to exist between computations $A$ and $B$ \textit{iff} (1) $A$ executed the expression \code{await B}, or (2) the system enforces dynamic extent (see \Cref{ssec:designdims:extent}) and $A$ executed \code{spawn B}.

\subsubsection{\Cooperation}
\label{ssec:designdims:cooperation}

The Cancellation Cooperation axis defines if a \coro receives a cancellation signal (awareness) and if it can react to that signal. We define cancellation as a property of a \coro because the \coro is the reification of the program code. Therefore, cooperative cancellation allows the developer to write code in an asynchronous function that reacts to a cancellation signal.

An async function in Rust gets rewritten into a \coro, a reification of the developers code as a state machine object. This state machine is periodically resumed by the runtime (if it's wrapped in a \task) or by manually polling the \coro (using a macro like \code{tokio::select}). When a \coro goes out of scope it invokes the value's destructor, just as with any other value. The default destructor for a Rust \coro simply deallocates the memory. Therefore, memory deallocation is a valid strategy to cancel the execution of a \coro. The implication of Rust's cancellation policy is that an async function may never be resumed after suspending, even if there's more work to be done. This form of cancellation is \textit{non-cooperative} because the state machine object is never aware that it's being cancelled and thus it cannot react to being cancelled.

\Cref{fig:cooperation:rust} provides an in-depth example of how this cancellation policy can quickly lead to bugs in business logic. The provided code in \Cref{fig:cooperation:rust:code} is an implementation of the checkout functionality for an e-commerce website. A common use case of mutexes is to temporarily \textit{violate} system invariants and release the lock after invariants have been restored. In this example the store's inventory is protected by a mutex, which the \code{checkout} function locks during checkout. The inventory for the purchased item is decremented and the payment processed. Acquiring the mutex lock and processing the payment are asynchronous operations that represent multiple states that the \coro can be in. \Cref{fig:cooperation:rust:client} shows an example of how the system might call \code{checkout} and racing its completion against a cancellation signal (by e.g., the user cancelling the purchase).

\Cref{fig:cooperation:rust:automaton,fig:cooperation:rust:swimlane} demonstrate how an an execution of the client code can lead to the e-commerce platform to lose inventory. The problem occurs when the user cancels the transaction while payment is processing. At this point the inventory has been decremented, but after the cancellation signal is received, Rust deallocates the \coro, which non-cooperatively cancels the continuation of the suspended \code{checkout} function. The deallocation releases the lock on the inventory before the invariant can be reinstated.

A widely known problem with Tokio mutexes is that they can be held across await points~\cite{paharia_400_2025,paharia_cancelling_2025}. If cancellation occurs during these awaits, the mutex lock is released and system-wide invariants can remain broken, which leads to subtle bugs.

In Python when a \coro goes out of scope its destructor is run, however, unlike Rust, the destructor will throw an exception \textit{into} the \coro object. By throwing into the \coro, Python ensures that finalizers are properly run for referenced objects. It also ensures that generators that can't be resumed do not remain part of an uncollectable reference cycle.

This cancellation policy provided by Python implies that a \coro becomes aware of its cancellation and developers can use this fact to properly perform cleanup and resinstate program invariants. \Cref{fig:cooperation:py} shows an example implementation of the e-commerce \code{checkout} function in Python using the Asyncio runtime. The Python implementation allows for the developer of \code{checkout} to increment the inventory when an error occurs during payment, this error includes an exception thrown to cancel the \coro.

Given the ability to perform cleanup, it may seem like an obvious win to choose a cooperative cancellation mechanism. However, there are benefits and drawbacks to both styles. We showed previously that non-cooperative cancellation can lead to broken program invariants because a \coro value cannot clean up used resources or restore broken invariants. Nevertheless, non-cooperative cancellation guarantees that a cancelled \coro performs no further asynchronous work, and therefore, terminates.\footnote{Assuming that destructing the \coro value terminates. Destruction cannot perform asynchronous work.}

\subsubsection{Propagation direction}
\label{ssec:designdims:direction}

The Propagation Direction axis defines how a cancellation signal propagates through the graph of dependent \tasks. The possible values are \textit{top-down,} \textit{bottom-up,} and \textit{simultaneous.} For languages with cooperative cancellation, if the propagation direction is not simultaneous then it is possible to suppress cancellation for dependents or dependees, depending on the chosen direction.

Rust employs top-down cancellation propagation. Consider again the Tokio (Rust) code in \Cref{fig:cooperation:rust}. When the \coro value --- in the unexecuted state \circled{C} --- is deallocated, the standard destructor procedure is run. Destructors run recursively, that is, they run top-down in the dependency graph. Rust developers cannot customize the destructor behavior for compiler-generated \coros, however, the logic bug highlighted in \Cref{fig:cooperation:rust:swimlane} could be avoided by creating a custom struct that mimicks the \coro interface.

\Cref{fig:cancellation:dir:rust} provides a scaffolded program to implement a custom destructor. By manually implementing the \coro abstraction, developers can customize the destructor behavior and increment the inventory if the \coro is dropped before \circled{C} executes. This ``solution'' is not satisfying because devlopers need to manually implement the state machine as the compiler would have generated it, but it is also not a total solution. Destructors in Rust cannot perform asynchronous operations, so cleanup logic that requires asynchronous work are inexpressible.

Python employs bottom-up cancellation propagation. Consider the Asyncio (Python) code in \Cref{fig:cooperation:py}. When the \coro associated with \code{checkout} is destroyed, a cancellation exception is thrown into the \coro, temporarily resuming the code for finalizers to run. The exception is raised at the next possible await point, which is the deepest await point in the dependency graph that suspended the computation.

Python's cooperative cancellation policy allows for developers to react to cancellation and perform necessary clean up, but it also leaves the door open for cancellation signals to be suppressed. \Cref{fig:cancellation:dir:py} shows an example implementation of the \code{process_payment} function that uses a bare exception handler. This handler suppresses the cancellation exception raised by the runtime, which results in the same bug as demonstrated by Rust's non-cooperative cancellation.

Swift provides \textit{simultaneous} cancellation, which alerts all tasks in the dependency graph at the same time. Although it is idiomatic to raise an exception when cancelled, \tasks can check the property \code{Task.isCancelled} to learn if they've been marked for cancellation. Swift cancellation is cooperative, allowing \tasks to perform cleanup code, but the simultaneous cancellation signal to all nodes in the dependency graph ensures communication of the cancellation.
