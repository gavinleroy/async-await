\subsection{Cancellation}\label{ssec:designdims:cancellation} The Cancellation axis defines how a running task is cancelled, including how cancellation is signaled, if at all, and how a cancellation signal propagates through the task tree. A clear cancellation mechanism is an important feauture of the asynchronous programming paradigm. Cancellation is a sufficiently complex mechanism that it itself contains two design dimensions:\textit{cooperation,} and \textit{direction.}

\subsubsection{Cooperation} The Cancellation Cooperation axis defines if a \bum receives a cancellation signal (awareness) and if it can react to that signal. We define cancellation as a property of a \bum because the \bum is the reification of the program code. Therefore, cooperative cancellation allows the developer to write code in an asynchronous function that reacts to a cancellation signal.

An async function in Rust gets rewritten into a \coro, a reification of the developers code as a state machine object. This state machine is periodically resumed by the runtime (if it's wrapped in a \task) or by manually polling the \coro (using a macro like \code{tokio::select}). When a \coro goes out of scope it invokes the value's destructor, just as with any other value. The default destructor for a Rust \coro simply deallocates the memory. Therefore, memory deallocation is a valid strategy to cancel the execution of a \coro. The implication of Rust's cancellation policy is that an async function may never be resumed after suspending, even if there's more work to be done. This form of cancellation is \textit{non-cooperative} because the state machine object is never aware that it's being cancelled and thus it cannot react to being cancelled.

\Cref{fig:cooperation:rust} provides an in-depth example of how this cancellation policy can quickly lead to bugs in business logic. The provided code in \Cref{fig:cooperation:rust:code} is an implementation of the checkout functionality for an e-commerce website. A common use case of mutexes is to temporarily \textit{violate} system invariants and release the lock after invariants have been restored. In this example the store's inventory is protected by a mutex, which the \code{checkout} function locks during checkout. The inventory for the purchased item is decremented and the payment processed. Acquiring the mutex lock and processing the payment are asynchronous operations that represent multiple states that the \coro can be in. \Cref{fig:cooperation:rust:client} shows an example of how the system might call \code{checkout} and racing its completion against a cancellation signal (by e.g., the user cancelling the purchase).

\Cref{fig:cooperation:rust:diag1,fig:cooperation:rust:diag2,fig:cooperation:rust:diag3} show the state transition diagrams that can lead to a loss of inventory without selling any actual merchandise. The problem occurs when the user cancels the transaction while payment is processing. At this point, the inventory has already been decremented, but after the cancellation signal is received the \coro is deallocated. A widely known problem with Tokio mutexes is that they can be held across await points~\cite{paharia_400_2025,paharia_cancelling_2025}. If cancellation occurs during these awaits, the mutex lock is released and system-wide invariants can remain broken, which leads to subtle bugs.

In Python when a \coro goes out of scope its destructor is run, however, unlike Rust, the destructor will throw an exception \textit{into} the \coro object. By throwing into the \coro, Python ensures that finalizers are properly run for referenced objects. It also ensures that generators that can't be resume do not remain part of an uncollectable reference cycle.

This cancellation policy provided by Python implies that a \coro becomes aware of its cancellation and developers can use this fact to properly perform cleanup and resinstate program invariants. \Cref{fig:cooperation:python} shows an example implementation of the e-commerce \code{checkout} function in Python using the Asyncio runtime. The Python implementation allows for the developer of \code{checkout} to increment the inventory when an error occurs during payment, this error includes an exception thrown to cancel the \coro.

Given the ability to perform cleanup, it may seem like an obvious win to choose a cooperative cancellation mechanism. However, there are benefits and drawbacks to both styles. We showed previously that non-cooperative cancellation can lead to broken program invariants because a \coro value cannot clean up used resources or restore broken invariants. Nevertheless, non-cooperative cancellation guarantees that a cancelled \coro performs no further asynchronous work, and therefore, terminates.\footnote{Assuming that destructing the \coro value terminates. Destruction cannot perform asynchronous work.}

\subsubsection{Propagation direction}

\ggnote{This paragraph has not been updated}

The Propagation Direction axis defines where in the waiting tree of dependencies cancellation is signaled first and how that signal is propagated to the rest of the waiting nodes. The possible values are \textit{top-down,} \textit{bottom-up,} and \textit{simultaneous.}

Before specifying exactly what the direction of cancellation propagation is, we first need to specify through what cancellation is propagating. Cancellation propagates through the \textit{task tree,} specifically, the task tree rooted at the cancelled task. Not all languages explicitly build a task tree in the runtime.

Consider the Rust (SMOL) code in \Cref{fig:cancellation}, at line fifteen, the set of tasks is depicted in \Cref{fig:cancellation:tree:rust}. Unlike Python, an edge between two tasks in the SMOL task tree is added when a task is \textit{spawned,} not when it's awaited. We say this because the calling task has ownership of the spawned task. When a task is cancelled, SMOL invokes the destructors as they would typically run in Rust, which flows down the tree represented by memory ownership. Therefore, we say that Rust (SMOL) cancellation propagates top-down.

Consider the Python (Asyncio) code in \Cref{fig:cancellation}, at line 11, the set of tasks is depicted in \Cref{fig:cancellation:tree:python}. By default, all tasks in Asyncio are disjoint. Given two tasks, $A$ and $B$, where $B$ is spawned from within $A$, an edge in the task tree is added between the two nodes only when $A$ awaits $B$. Therefore, in our example program \code{db_update} is a child of \code{process} only because of the await present on line eleven. Therefore, cancellation is signalled from within \code{update_db}, and propagates \textit{upward} in the task tree to signal cancellation.

A \textit{simultaneous} cancellation would alert all tasks at the same time of cancellation. An example language with simultaneous cancellation propagation is Swift, as we will see in \Cref{sec:semantics}.
