\subsection{Destruction}\label{ssec:designdims:destruction} The \Task Destruction axis defines what happens to a task at the end of its extent (see \Cref{sssec:dims:extent}) and is destructed. The possible values are: \textit{awaited,} \textit{cancelled,} or \textit{terminated.}

\Cref{fig:designdims:destruction:await} shows an example JavaScript program that waits for an unawaited \task to complete, even though there is no explicit \code{await} keyword. The program terminates after 10 seconds and prints ``exiting'' and ``done.''

\Cref{fig:designdims:destruction:cancel} shows an example Swift program that cancels a running task on destruction. Because that task is executing a long sleep operation, the sleep is cancelled --- on cancellation \code{Task.sleep} raises an exception that we suppress with the \code{try?} keyword --- and the program continues executing. The program terminates after ~0.5 seconds and prints ``exiting,'' ``cancelled'' and ``done.''

\Cref{fig:designdims:destruction:term} shows an example \CSharp program that terminates running \tasks on destruction. The program terminates after ~0.5 seconds and prints ``exiting.''

\begin{figure}[H]
  \begin{subfigure}[t]{0.30\textwidth}
\begin{lstlisting}[language=JavaScript,escapechar=|]
async function inner() {
  await new Promise(r =>
    setTimeout(r, 10_000))
  console.log("done")
}

async function work() {
  let a = inner()
  await new Promise(r =>
    setTimeout(r, 0))
  console.log("exiting")
}

await work() // ~10s
\end{lstlisting}
    \cprotect\caption{JavaScript awaits all running tasks at the end of their scope (program scope). The execution of the above program takes about 10 seconds and prints ``exiting,'' and ``done,'' because the leaked \task is fully awaited.}
    \label{fig:designdims:destruction:await}
  \end{subfigure}\hfill%
  \begin{subfigure}[t]{0.32\textwidth}
    \begin{lstlisting}[language=Swift,escapechar=|]
func inner() async {
  try? await Task.sleep(
      for: .seconds(10))
  if Task.isCancelled {
    print("cancelled")
  }
  print("done")
}

func work() async throws {
  async let _ = inner()
  try await Task.sleep(
      for: .seconds(0))
  print("exiting")
}

try await work() // ~0.5s
\end{lstlisting}
    \cprotect\caption{Swift cancels all running tasks on destruction. The execution of the above program takes about 0.5 seconds and prints ``exiting,'' ``cancelled,'' and ``done.''}
  \label{fig:designdims:destruction:cancel}
\end{subfigure}\hfill%

\begin{lstlisting}[language=CSharp,escapechar=|]
async Task InnerWork() {
  await Task.Delay(10_000);
  Console.Write("done");
}

async Task Work() {
  var _ = InnerWork();
  await Task.Delay(0);
  Console.Write("exiting");
}

async Task Main() {
  await Work();
} // ~0.5s
\end{lstlisting}

Where your language falls on the destruction axis informs the safety and responsiveness of the system. Awaited destruction prioritizes data integrity and completeness at the expense of responsiveness. Cancel destruction allows \tasks to safely reclaim resources --- depending on the language's chosen cancellation semantics, see \Cref{} --- however, programs may still suffer from responsiveness issues if cancelling a \task takes too long (or doesn't terminate). Terminate destruction prioritizes speed over safety. A running \task may hold system resources or be in the middle of an operation, by cancelling the \task the system risks deadlocks and breaking logical invariants.
