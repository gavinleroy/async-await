\section{Defining Asynchrony}\label{sec:motivation}

Async/await is about expressing \emph{asynchronous programming}, or more simply, \emph{asynchrony}. Asynchrony is related to, but not the same as, concurrency or parallelism. Many prior works have offered their own definition of asynchronous programming. For instance, \citet{spl:fsharp-async} say that ``asynchronous programming is characterized by many simultaneously pending reactions to internal or external events.'' While a reasonable starting point, our goal in this paper is to offer an expanded view on asynchrony that encompasses the full scope of features found in modern languages.

\subsection{Asynchrony vs. Concurrency vs. Parallelism}

We will define concurrency as a logical property of a computation, whereby two subcomputations can execute interleaved: one computation begins before another ends. Parallelism is a physical property of a computation, whereby two subcomputations can execute simultaneously: both compuations overlap at the same point in time. Parallelism implies concurrency but not vice versa. For instance, an embedded operating system running on a single core is concurrent but not parallel.

Concurrency and parallelism have programming paradigms. Paradigms of concurrent computing include shared-memory concurrency (e.g., POSIX C), communicating sequential processes (Open MPI, Go), and actors (Erlang). Paradigms of parallel computing include fork-join parallelism (Cilk, OpenMP), collection parallelism (MapReduce, Spark), and index-space parallelism (OpenGL, CUDA).  Like all paradigms, these labels are useful but leaky, such as how complex parallel programs often involve shared-memory concurrency. Ultimately, a paradigm is about focusing a set of related mechanisms (\verb|spawn|, mutexes) on a set of related problems (sorting a list, running a database).

Asynchrony also has paradigms. Callback asynchrony uses higher-order functions to provide a continuation for the completion of a computation, most notably found in \CSharp{}, Javascript, and Swift. Event-loop asynchrony structures a program around a main loop that dispatches reactions to an event stream, most notably found in C++ and Rust. Languages have historically developed async/await to address the ergonomic problems associated with these two asynchrony paradigms. More generally, a key motivation is to provide a surface syntax for concurrent code that looks comparable to non-concurrent (synchronous) code. For example, below are excerpts from async/await proposal documents across a few languages:

\begin{displayquote}%c#
  \textbf{(\CSharp{})} Notice first how similar it is to the synchronous code. \ldots The control flow is completely unaltered, and there are no callbacks in sight. That doesn’t mean that there are no callbacks, but the compiler takes care of creating and signing them up \ldots~\cite{torgersen_asynchronous_nodate}
\end{displayquote}

%   \textbf{(JavaScript)} With async functions, all the remaining boilerplate is removed, leaving only the semantically meaningful code in the program text.~\cite{noauthor_async_nodate-1}

\end{displayquote}

We will define the paradigm encompassing async/await as \emph{straight-line asynchrony}, given its fundamental organizing principle of eliminating complex control flow in source code to present straight-line code.

\subsection{Straight-line Asynchrony}

The goal of this paper is to explore the design space of straight-line asynchrony. We primarily focus on programming languages that (a) have a relatively settled design for straight-line asynchrony, and (b) are in relatively widespread use. That includes languages with a singular form of asynchrony: \Js (specifically ECMAScript XX, with Typescript types for clarity), \CSharp (vXX), and Swift (vXX). It also includes languages with a modular form of asynchrony: Python (v3.14, using Asyncio vXX and Trio vXX) and Rust (v1.92.0, with Tokio vXX and \smol vXX). We discuss how our findings relate to other languages in \Cref{sec:discussion}.

We will describe our findings informally in \Cref{sec:designdims} and formally in \Cref{sec:semantics}. We do not expect our readers to be familiar with the concrete syntax of all relevant languages, so we will articulate the design dimensions at a high-level, and present code examples primarily using the same pseudocode style in \Cref{fig:motivating-example}. However, it will be useful to first get a sense for both the gestalt and the variety of asynchronous programming syntaxes, mechanisms, and semantics. We will therefore conclude this section by implementing an async utility in each language.

Consider implementing a \verb|timeout| function, which takes as input an asynchronous function and a duration. The minimal semantics is that \verb|timeout| returns either the result of the asynchronous work, or if the work takes longer than the duration, an indication of timing out. The \verb|timeout| function is a good exemplar of asynchronous programming, as its implementation is often non-trivial when only using primitives from other concurrency or parallelism paradigms.

\Cref{fig:timeout-simple} shows three implementations of the minimal \verb|timeout| semantics. Most straight-line async designs include a race primitive (also called \verb|select|, \verb|or|, \verb|wait|, \verb|next|) which returns the first of several asynchronous computations to complete, as shown in the \Js and Rust+Tokio examples.  Notably, some designs like Trio offer a different set of primitives, so \verb|move_on_after| is essentially a timeout primitive which cannot be implemented by the user.

An enhanced semantics for \verb|timeout| should take into account \emph{cancellation}. Cancellation is another core concept for asynchrony, which did not feature prominently in earlier designs such as \Js and \CSharp, but is more consciously part of later designs such as Swift and Python. For \verb|timeout|, we desire two properties. First, if a computation exceeds the duration, the computation is cancelled. Seconds, if the \verb|timeout| is cancelled, then its child async computations are also cancelled. The cancellation should happen such that the child computation can execute cleanup code before terminating.

\begin{figure}[ht!]
\begin{subfigure}{0.53\linewidth}
  \begin{lstlisting}[language=Rust]
async fn timeout<T, Fut>(
  duration: Duration,
  token: CancellationToken,
  f: impl FnOnce(CancellationToken) -> Fut,
) -> TimeoutResult<T>
where
  T: Send + 'static,
  Fut: Future<Output = T> + Send + 'static,
{
  let mut handle = tokio::spawn(
    f(token.child_token()));
  tokio::select! {
    result = &mut handle => 
      TimeoutResult::Success(result.unwrap()),
    _ = token.cancelled() => 
      TimeoutResult::Cancelled,
    _ = sleep(duration) => {
      token.cancel();
      TimeoutResult::TimedOut
    }
  }
}
\end{lstlisting}
\caption{Rust+Tokio}
\end{subfigure}%

  \begin{lstlisting}[language=Swift]
func timeout<T: Sendable>(
  duration: Duration,
  f: @Sendable () async throws -> T
) async throws -> T? {
  try await withoutActuallyEscaping(f) { 
    f in
    try await withThrowingTaskGroup { 
      group in
      group.addTask { try await f() }
      group.addTask {
        try await Task.sleep(
          for: duration)
        return nil
      }
      defer { group.cancelAll() }
      return try await group.next()!
    }
  }
}
\end{lstlisting}
\caption{Swift.}
\end{subfigure}
  \cprotect\caption{An enhanced implementation of \verb|timeout|, which handles cancellation both from within and without the function.}
  \label{fig:timeout-cancel}
\end{figure}

\Cref{fig:timeout-cancel} shows two implementations of the enhanced \verb|timeout| semantics. The Rust+Tokio function uses an explicit data structure, the \verb|CancellationToken|, threaded throughout the code. This token is a signal for a set of related tasks to end. To enable \verb|timeout| to cancel its child computation, the token is passed to \verb|f|, which should (by convention!) react to the token. To enable a caller to cancel \verb|timeout|, the token's cancellation event is handled in the \verb|select!| expression. This style of explicit cancellation is akin to that found in Javascript (via \verb|AbortController| and \verb|AbortSignal|) and \CSharp (via \verb|CancellationToken|). Note that one could alternatively implement the Rust+Tokio code without a cancellation token by calling \verb|handle.abort()|, which terminates the computation at the next await point. This strategy would still invoke Rust's standard \verb|Drop| handlers that precede memory deallocation, but it would not permit for any more customized cleanup code.
